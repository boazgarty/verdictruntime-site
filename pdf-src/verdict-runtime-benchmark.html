The layer the static scanners don’t have LIVE PROOF

9 additional vulnerabilities confirmed by actually exploiting three of the running apps

Verdict Runtime doesn’t just read code: its agents send real, scope-authorised requests and prove each finding against the live application, with a reproducing request each:

  • Broken object authorisation (BOLA/IDOR) — one account read another account’s private data
  • Authentication-token forgery — an unsigned (alg:none) token accepted as valid
  • Exposed admin / debug surfaces — internal config and server logs served to an unauthenticated request
  • Missing login rate-limiting & weak session cookies

Static scanners, the commercial tool and CodeQL included, cannot prove any of these. Broken authorisation and token forgery are logic flaws that only show up when you exercise the live application.

Method & scope. Ten deliberately vulnerable open-source training applications in five languages (JavaScript/TypeScript, Python, Java, Go, C#), each scored against an answer key built from the app’s own labels; a detection counts only when the correct vulnerability class is reported within ±3 lines. Each competing scanner ran at its documented security settings (the commercial tool's default security rules; CodeQL security-extended suites); Verdict Runtime ran its standard code, secrets and infrastructure-as-code scan. The Python benchmark is synthetic and an early release; one run per tool (Verdict Runtime 2026-11-04, commercial SAST tool 2026-10-23). The live-proof results come from Verdict Runtime’s agents against disposable, explicitly authorised local instances. These are labelled training targets, so the results show a measured lead on this suite, not a claim of universal superiority. CodeQL is a trademark of GitHub, Inc.
